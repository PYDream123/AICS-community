## 1. 产品概述

### 1.1 产品定位

面向中小型 B 端企业的智能客服平台。企业将产品文档、售后政策等资料上传后，平台对外提供基于大模型的自动问答能力，并在无法回答时平滑转交人工。

核心差异在于**不是"聊天机器人"，而是"能查资料、能办业务、知道何时该认输"的客服**：

- 回答有出处（引用原文片段），可被追溯；
- 能调用业务工具完成查订单、查物流、建工单等动作，而不只是回答；
- 答不上来时不编造，主动转人工。

### 1.2 MVP 目标

**跑通一条完整的客服闭环，并用数据证明效果。**

具体表现为：上传资料 → 用户提问 → 流式回答并给出引用 → 需要业务数据时调用工具 → 答不上来转人工，全链路可在浏览器中演示；同时具备一套可复跑的评测数据，能量化回答质量。

MVP 不追求多租户、高并发与生产级运维能力，追求的是**链路完整、逻辑可解释、效果可度量**。

### 1.3 目标用户与角色

| 角色 | 描述 | MVP 中的形态 |
|------|------|--------------|
| 终端用户 | 企业客户，通过网页对话框提问 | 单页聊天界面 |
| 知识库管理员 | 维护问答所依据的资料 | 文档上传与列表管理（简易） |
| 人工客服 | 接管 AI 无法处理的会话 | 转人工待处理队列（仅记录，不含坐席工作台） |
| 平台运营/开发者 | 关注回答质量与系统表现 | Trace 查看 + 评测脚本（命令行） |

> MVP 阶段不区分租户，所有数据属于单一企业实例；表结构中预留租户字段，但不实现隔离逻辑。

## 2. 核心使用场景

### 场景一：售后政策咨询（RAG 主链路）

用户询问"七天无理由退货的运费谁承担"。系统检索售后政策文档，命中相关段落，流式给出回答并标注来源为《售后服务政策 v3》第 2.3 节。用户可展开查看原文片段。

### 场景二：订单状态查询（工具调用）

用户询问"我的订单什么时候到"。系统识别出需要订单数据，先向用户索取订单号（槽位补齐），再调用订单查询工具，将结构化结果组织成自然语言回复。

### 场景三：多轮追问（记忆）

用户先问"你们的保修期多久"，再追问"那过了保修期维修怎么收费"。系统需理解"那"指向保修话题，不能当作孤立问题重新检索。

### 场景四：超出知识范围（兜底）

用户询问一个知识库中完全没有的问题，例如"你们公司在东南亚有代理吗"。检索相似度低于阈值，系统明确表示"暂无相关资料"，并提供转人工入口，会话进入待处理队列。

## 3. 功能架构

```
AICS MVP
├── 知识库管理
│   ├── 文档上传（Markdown / TXT）
│   ├── 文档列表与删除
│   └── 自动切片与向量化入库
├── 对话服务
│   ├── 流式问答（SSE）
│   ├── 引用溯源
│   ├── 多轮记忆
│   └── 低置信兜底
├── 工具调用
│   ├── 订单查询
│   ├── 物流查询
│   └── 工单创建
├── 人工接管
│   └── 转人工队列
└── 质量与可观测
    ├── 请求 Trace（召回、耗时、token）
    └── 评测集与指标脚本
```

功能按四组划分：**知识（喂什么）、对话（怎么答）、工具（能办什么事）、质量（答得好不好）**。前三组构成用户可见的产品能力，第四组是支撑持续优化的基础设施。

## 4. 功能说明

### 4.1 知识库管理

**目标**：让非技术人员能把资料变成可检索的知识，不需要理解向量、切片等概念。

| 能力 | 说明 | 验收要点 |
|------|------|----------|
| 文档上传 | 支持 .md / .txt，单文件 ≤ 10MB；上传后自动完成解析、切片、向量化 | 上传成功即立即可被检索到，无需额外操作 |
| 文档列表 | 展示文件名、大小、切片数、状态（处理中/可用/失败）、上传时间 | 失败时能显示原因，可重试 |
| 文档删除 | 删除文档时同步清除其全部切片与向量 | 删除后该文档内容不再出现在回答中 |
| 切片策略可配 | 切片长度、重叠长度可通过配置调整 | 修改配置后新建文档生效；已有文档可在重建时应用 |

**边界**：MVP 只处理纯文本类格式。PDF、Word、扫描件解析明确不做，避免陷入格式兼容的泥潭。

### 4.2 对话服务

**目标**：提供一个"像人但不乱说"的问答体验。

| 能力 | 说明 | 验收要点 |
|------|------|----------|
| 流式问答 | 基于 SSE 逐字返回，用户无需等待完整生成 | 首字延迟 ≤ 1.5s（MVP 目标，非承诺值） |
| 引用溯源 | 回答下方展示本次命中的知识片段及来源文档，可展开查看原文 | 每个基于知识库的回答至少携带 1 条引用；无引用时不得声称"根据资料" |
| 多轮记忆 | 会话上下文持久化，取最近 N 轮进入 Prompt；超长时压缩为摘要 | 连续 8 轮对话不丢失前文关键信息；上下文不超模型窗口 |
| 低置信兜底 | 召回相似度全部低于阈值时不生成答案，直接返回"暂无相关资料"并提示转人工 | 阈值可配；不得对无依据问题编造回答 |
| 会话管理 | 支持新建会话、查看历史会话列表 | 刷新页面后历史会话可恢复 |

**设计原则**：宁可承认不知道，也不要给一个看起来合理但错误的答案。客服场景下，错误回答的成本远高于"我不知道"。

### 4.3 工具调用

**目标**：让 Agent 从"会说话"变成"能办事"。

MVP 提供三个工具，覆盖查询类与写入类两种形态：

| 工具 | 类型 | 输入 | 输出 |
|------|------|------|------|
| 订单查询 | 只读 | 订单号 | 订单状态、下单时间、金额、商品摘要 |
| 物流查询 | 只读 | 订单号 | 承运商、运单号、最新物流节点 |
| 工单创建 | 写入 | 问题描述、联系方式、会话 ID | 工单号、预计响应时间 |

**共用要求**：

- 工具由模型自主决策是否调用，不由前端写死触发条件；
- 参数缺失时由 Agent 向用户追问补齐，而不是直接报错；
- 参数校验失败、调用超时、下游异常时，给出用户可理解的降级话术，不暴露技术细节；
- 写入类工具需保证幂等，同一会话重复提交不产生重复工单；
- MVP 阶段工具对接本地模拟数据（20 条量级），接口形态按真实业务设计（含错误码、幂等键），便于后续替换为真实服务。

### 4.4 人工接管

**目标**：给 AI 的能力边界一个出口。

| 能力 | 说明 |
|------|------|
| 主动转人工 | 用户在对话中点击"转人工"，会话标记为待接管 |
| 被动转人工 | 触发低置信兜底、或工具连续失败时，系统主动建议转人工 |
| 队列记录 | 落库保存会话 ID、转人工原因、用户问题摘要、时间；提供查询接口 |

**边界**：MVP 不做坐席工作台、不做实时双向会话、不做排队与分配策略。目标只是把"该转人工的会话"可靠地识别并记录下来。

### 4.5 质量与可观测

**目标**：让"效果好不好"从主观感受变成可查的数字。这是 MVP 中最容易被省略、但对后续所有优化最关键的部分。

| 能力 | 说明 |
|------|------|
| 请求 Trace | 每次问答记录：用户问题、召回片段及相似度、是否触发工具、各阶段耗时、token 用量、最终回答 |
| 评测集 | 20–40 条人工标注的问答对，每条标注期望命中的文档片段 |
| 指标脚本 | 可重复执行，输出 Recall@k、引用准确率、拒答准确率、平均首字延迟 |

**说明**：Recall@k 衡量"该找到的找到了没有"；拒答准确率衡量"该说不知道的时候有没有硬答"。这两项是 RAG 系统最核心的健康指标。评测集建立后，任何检索策略、切片参数、Prompt 的调整都必须先跑一轮对比再决定是否采纳。

## 5. 端到端主流程

```
管理员上传文档
      → 系统解析、切片、向量化入库
            ↓
用户发起提问
      → 检索相关片段（top-k + 相似度过滤）
            ↓
  相似度是否达标？
   ├─ 否 → 提示暂无资料 → 建议转人工 → 会话入队
   └─ 是 → 组装上下文（系统提示 + 片段 + 近 N 轮历史）
            ↓
      模型判断是否需要工具
       ├─ 需要 → 校验参数 → 调用工具 → 结果并入上下文 → 二次生成
       └─ 不需要 → 直接生成
            ↓
      SSE 流式返回 + 引用片段
            ↓
      记录 Trace
```

## 6. 非功能性要求（MVP 级）

| 维度 | MVP 要求 |
|------|----------|
| 部署形态 | 单体应用 + Docker Compose 一键启动依赖（数据库等），本机可运行 |
| 并发能力 | 支持 10 路并发对话不报错、不串话，不追求吞吐指标 |
| 数据一致性 | 会话与消息落库，进程重启后历史可恢复 |
| 可配置性 | 检索 top-k、相似度阈值、切片参数、记忆轮数均可配置，不写死在代码里 |
| 可替换性 | 模型、Embedding 服务通过配置切换，不绑定单一供应商 |
| 安全 | 不记录用户敏感信息明文；工具调用参数日志脱敏 |

## 7. MVP 明确不做

以下能力在方案全量版中存在，但**明确排除在 MVP 之外**，避免范围蔓延：

- 多租户隔离与租户级限流
- 坐席工作台、实时人工对话、排队分配
- PDF / Word / 扫描件解析
- 混合检索（BM25 + 向量）与重排模型接入
- 消息队列削峰、独立日志检索系统、容器编排与监控告警
- 微服务拆分与注册中心
- 对话质量自动评估（LLM-as-judge）

> 其中「混合检索与重排」属于 MVP 之后的第一个优化实验，需以评测集数据为依据决定是否引入，见第 9 节。

## 8. 成功指标

### 8.1 产品指标

| 指标 | 定义 | MVP 目标 |
|------|------|----------|
| 自动解决率 | 未转人工且用户未重复追问的会话占比 | ≥ 60%（人工抽查口径） |
| 转人工率 | 触发转人工的会话占比 | ≤ 30% |
| 引用覆盖率 | 知识类回答中携带有效引用的比例 | 100% |
| 首字延迟 | 从提问到首字返回的耗时 | ≤ 1.5s |

### 8.2 技术指标

| 指标 | 定义 |
|------|------|
| Recall@5 | 评测集中，期望片段出现在 top-5 召回结果的比例 |
| 引用准确率 | 引用片段确实支撑回答的比例（人工抽样判定） |
| 拒答准确率 | 无答案问题被正确拒答的比例 |

指标基线在评测集建成后确定，不预先编造数字。所有对外表述的准确率必须来自评测集的实际运行结果。

## 9. 迭代规划

| 里程碑 | 范围 | 完成标准 |
|--------|------|----------|
| M0 骨架 | 工程初始化、依赖服务启动、模型调用打通、SSE 返回固定内容 | 浏览器可见流式输出 |
| M1 单轮问答 | 知识库管理 + 检索问答 + 引用 + Trace | 上传 10 篇文档、20 个问题可人工验证命中情况，产出首版 Recall@5 |
| M2 多轮记忆 | 会话与上下文管理 | 连续 8 轮对话上下文不丢失、不超窗口 |
| M3 工具调用 | 三个工具 + 参数校验 + 降级 | 三类意图均能正确触发，异常路径有友好提示 |
| M4 兜底与交互 | 低置信兜底、转人工、单页前端 | 四类核心场景可完整演示，5 分钟不中断 |
| M5 效果优化 | 混合检索、重排、切片策略对比实验 | 用评测集产出优化前后对比数据 |

M0–M4 构成本次 MVP 的交付范围；M5 属于后续迭代，其产出直接用于形成量化的效果结论。

## 10. 风险与假设

| 风险 | 影响 | 应对 |
|------|------|------|
| 模型输出不稳定，同一问题多次回答不一致 | 影响演示效果与指标统计 | 固定温度参数；关键路径用结构化输出约束；评测时多次采样取均值 |
| 本地模拟业务数据过于单薄 | 工具调用场景缺乏说服力 | 模拟数据覆盖正常、异常、边界三类用例（订单不存在、已取消、无物流） |
| 切片与检索调优耗时超预期 | 拖慢整体进度 | 先固定一版基线参数跑通链路，优化统一放到 M5，用评测集驱动 |
| Embedding / 模型调用成本 | 影响持续调试 | 开发阶段用小规模文档集；Embedding 结果缓存，避免重复计算 |

**关键假设**：

1. 单一企业实例、单一知识域，不涉及跨租户数据隔离；
2. 知识以文档形式存在，可离线整理为纯文本，不依赖实时业务系统；
3. 演示环境为本地单机，无真实并发压力要求。
